Corely Gap Analysis

Audit date: 2026-10-04 · Product owner: Krishil Agrawal · Branch: master

We read through the whole Corely codebase to find out what really works. The short answer: a lot of the app looks finished, but much of it is not. Some API routes let anyone read or delete another company's data. A real email password is written in the code. Slack and Linear content never becomes searchable, and syncs can get stuck forever. Many dashboard numbers are made up, and many buttons do nothing. Large parts, like automatic syncing, team invites and billing, were never built. This page lists every problem with the exact file and line, and ends with a phased plan to fix them, starting with the security holes.

How this was checked

We ran 4 separate read-only audits. "Read-only" means we only read code; we changed nothing. Each audit covered one area:

  1. The frontend (the pages and components people see).
  2. The API routes and the shared lib/ code.
  3. The connectors (the code that pulls data from Notion, Gmail and so on) and retrieval (how Ask Corely finds answers).
  4. The data model, the old planning notes, the landing pages and production readiness.

Where the audits disagreed, we went back and checked the code by hand. These 5 facts were confirmed by hand:

  • The background worker is never given work. workers/index.ts handles all 6 jobs (sync-google-drive, sync-notion, sync-gmail, sync-github, sync-slack, sync-linear, lines 76-111). But nothing adds jobs to the queue sourceQueue (lib/redis.ts:27).
  • Gmail incremental sync never runs. "Incremental" means fetching only what changed since last time. buildQuery (modules/sources/connectors/gmail.ts:136-150) returns config.query first. The Gmail callback always stores the query "newer_than:180d -category:promotions -category:social" (app/api/sources/gmail/callback/route.ts:95). So the incremental path is never reached. There is also a hard cap of 100 threads per sync.
  • Only Notion retries and cleans up. withRetry exists only in notion.ts (line 375). Only Notion removes documents that were deleted upstream (notion.ts:129-147). CLAUDE.md wrongly says all connectors do both.
  • A real password is in the code. lib/email.ts:6-7 has a real Gmail address and app password as a fallback. It was committed in 2cd2cb7.
  • Anyone can claim a password-less account. app/api/auth/login/route.ts:72-78 sets the password for any user who has no passwordHash.

Findings

Each item has a short claim, a plain explanation and the files involved. Badges show how serious it is: Critical for security holes, High for broken things that lose data or block users, Medium for everything else.

A. Security holes Critical

These let an outsider or a normal member see, change or delete data they should not. Fix these first.

CriticalA1. A real Gmail app password is leaked in the code.

The email helper uses a real Gmail address and app password as a fallback when the env variables are missing. It has been in git history since commit 2cd2cb7, so deleting the line is not enough. Rotate (replace) the password in Google first.

lib/email.ts:6-7 · commit 2cd2cb7

CriticalA2. Several API routes have no login check at all.

These routes look up a record by its id alone. They never call auth() and never check the workspace. Anyone who knows or guesses an id can act on another company's data:

  • app/api/chats/[sessionId]/route.ts GET/DELETE (lines 11-56)
  • app/api/chats/[sessionId]/messages/[messageId]/feedback/route.ts POST
  • app/api/documents/[documentId]/route.ts DELETE (lines 7-56)
  • app/api/sources/[sourceId]/route.ts DELETE (lines 7-27)
  • app/api/sources/[sourceId]/config/route.ts POST (12-28) — can set permissions:"everyone"
  • app/api/sources/[sourceId]/folders/route.ts GET — decrypts the stored Drive token
  • app/api/sources/[sourceId]/status/route.ts GET — leaks config and errorMessage
  • app/api/webhooks/drive and /notion POST (stubs)

CriticalA3. Login lets anyone take over an account that has no password.

The code block labelled "MVP Legacy Migration Logic" sets whatever password you type for any user without a passwordHash. That means the first person to log in with that email owns the account.

app/api/auth/login/route.ts:72-78

CriticalA4. Invites send the temporary password in plain text and return it in the API response.

The invite email contains the temporary password in plain text. The API response also returns it as _devPassword. The login link in the email is hardcoded to https://corely-khaki.vercel.app/login.

app/api/teams/members/route.ts:104-105 (password), line 81 (hardcoded link)

CriticalA5. Login tokens fall back to a public, known secret.

If JWT_SECRET is not set, session tokens (JWTs, signed login tokens) are signed with "fallback-secret-for-development-only". Anyone who reads the code can then forge a login for any user.

lib/auth-server.ts:6

CriticalA6. OAuth state tokens may double as login cookies. plausible, not proven

OAuth "state" is a value sent to Google, Notion and others and checked when they send the user back. Corely signs it with the same session key (encrypt from lib/auth-server.ts) and puts userId and workspaceId inside. So it is likely usable as a corely_session cookie for 24 hours. This is plausible but not proven. The nonce (a one-time random value) comes from Math.random and is never checked in the callbacks.

lib/auth-server.ts (encrypt) · OAuth connect/callback routes

CriticalA7. Ask Corely does not check that a chat belongs to you.

/api/ask takes a sessionId but never checks that the session belongs to the caller's workspace. Someone could read history from, or write into, another workspace's chat.

app/api/ask/route.ts:103-123

CriticalA8. Any member can do admin-only actions.

There is no permission check on these actions. Any member can:

  • create roles with any permissions (teams/roles/route.ts:31-46) — including giving themselves full admin;
  • rename the workspace or change its slug (settings/route.ts:65-81);
  • create and revoke API keys (settings/api-keys).

CriticalA9. "Permission-aware" search restricts nothing.

All 4 default roles include sources:read. That permission gives access to every source in the workspace. So every user sees everything, even private sources.

lib/rbac.ts:26-55 · ask/route.ts:146 · search/route.ts:54

CriticalA10. The dashboard is only protected in the browser.

There is no middleware.ts (server code that runs before a page loads). The dashboard is only protected by a redirect in the browser. An unauthenticated visit to /dashboard throws an error into error.tsx.

app/lib/auth-context.tsx:65-70

CriticalA11. Other account and crypto weaknesses.

  • Password-reset tokens are stored in plain text (forgot-password:29).
  • Forgot-password reveals whether an account exists: it returns a 500 error only when the user exists (line 45).
  • Logout only deletes the cookie. There is no session revocation (no way to kill a token on the server).
  • Changing your password does not end your other sessions.
  • The login rate limiter is an in-memory Map, per process, keyed by email (login/route.ts:14-17). It resets on restart and is not shared across servers.
  • Invite teamIds connect is not scoped to the workspace (teams/members:65), so you can add someone to another workspace's team.
  • lib/crypto.ts uses crypto-js AES in passphrase mode: key made with EVP_BytesToKey MD5, 1 iteration, AES-CBC, no MAC (no tamper check). decrypt returns "" on a wrong key instead of failing. crypto-js is discontinued.

B. Broken (built, but does not work)

The code for these exists, but it fails, gives wrong results, or silently does nothing.

Connectors and syncing

HighB1. Slack and Linear content can never be found by Ask Corely.

Both connectors first create a chunk row with prisma.documentChunk.create. Then they insert the same id again with supabaseAdmin into the same table (document_chunks). That fails with a duplicate key error. The insert is also missing the NOT NULL columns source_id and chunk_index. The error is only logged. The rows keep embedding=NULL, and the similarity filter skips them. Result: Slack and Linear content can never be retrieved.

slack.ts:243-251 · linear.ts:244-252

HighB2. Sources get stuck on "syncing" forever.

The sync route sets the status to syncing and then starts the connector without waiting ("fire-and-forget"). Connectors throw early errors (no token, refresh failure, "Gmail OAuth is not configured") before their try block. So the status never becomes error. Every retry then gets a 409 ("already syncing"). The Duplicate action creates copies without a token, and those always get stuck.

app/api/sources/[sourceId]/sync/route.ts:30-33 (starts sync) · route.ts:25-27 (409)

HighB3. Slack and Linear say "synced" without syncing anything.

After connecting, the callbacks set status "synced", lastSyncedAt to now and itemsIndexed 0, but no sync runs. Reconnecting Slack also overwrites the source config with just {teamId}.

slack/callback:76-93 · linear/callback:92-106

HighB4. There is no way to add GitHub from the UI.

The Add Source modal has cards only for Drive, Notion, Gmail, Slack and Linear (links at lines 262, 342, 421, 500, 578). "Configure Scope" shows only for google_drive.

SourcesMain.tsx:262,342,421,500,578 · SourcesMain.tsx:1328

MediumB5. The Sources page ignores most connect results and all errors.

It does not react to ?connected=github, ?success=slack_connected, ?success=linear_connected or any ?error=. Users get no message when a connect fails.

SourcesMain.tsx:773-791

HighB6. Drive folder picker shows fake folders.

When the token is missing, the list is empty, or there is an error, the route returns MOCK_FOLDERS ("Wednesday", "SAPUTARA", "Classroom"). If a user picks one, the sync finds 0 files and says nothing.

folders/route.ts:36-90

HighB7. Gmail only ever indexes the newest 100 threads.

Each sync fetches only the newest 100 threads from the last 180 days. Incremental sync never runs (see the hand-verified facts above). historyId is stored but never used.

modules/sources/connectors/gmail.ts:136-150 · app/api/sources/gmail/callback/route.ts:95

MediumB8. The sync schedule setting is thrown away.

The UI sends hourly / daily / weekly, but the config route ignores syncSchedule.

SourcesMain.tsx:1849 · config/route.ts:20

MediumB9. Saving source config can wipe chosen folders.

The config route deletes folderIds when they are not sent. It also does not check the source type.

app/api/sources/[sourceId]/config/route.ts

MediumB10. "Freshness" measures when we indexed, not when the content changed.

Document.updatedAt is @updatedAt, so it is set to the time of indexing. Only Linear and Slack pass the date from the source. So freshness scores are wrong for the other connectors.

prisma/schema.prisma (Document.updatedAt)

MediumB11. The "items indexed" count only goes up.

itemsIndexed only ever increments. It also counts changed documents again each time they are re-indexed.

Ask Corely

HighB12. The answer spinner never stops when there is no answer or an error.

The page handles only the sources and text SSE events (SSE: the stream of messages the server sends). The route also sends no_knowledge (line 191) and error (lines 82, 336). The page ignores them, so the user sees an endless spinner.

AskMain.tsx:525-544 · app/api/ask/route.ts:82,191,336

MediumB13. Thumbs up/down on a new answer always fails.

A new answer gets a local id corely-${Date.now()}. The server never returns the real database id, so feedback always 404s. Also, export checks feedback === "up", but the database stores "positive"/"negative".

AskMain.tsx:452/401 · export line 60

MediumB14. Links that pre-fill a question do nothing.

?q= is never read. No page under app/dashboard uses useSearchParams.

Links at Topbar.tsx:214,595,694 · insights/page.tsx:329

MediumB15. The Web Search and Knowledge Only toggles are ignored.

The page sends them, but the route reads only question and sessionId.

app/api/ask/route.ts:99

MediumB16. Share copies a link without the chat in it.

Share copies window.location.href, which has no session id. The person you share with cannot open the chat.

AskMain.tsx:306-311

MediumB17. PDF and DOCX attachments are read as garbage text.

Attachments are read with readAsText, which turns binary files like PDF and DOCX into unreadable text.

AskMain.tsx:285-290, 585

MediumB18. Follow-up questions lose their context in search.

Follow-ups like "what about last week?" are not rewritten into a full question. Only the latest question is embedded (turned into a vector for search), so search misses the topic.

ask/route.ts:158

Elsewhere

MediumB19. Dashboard health always says "Operational".

The check looks for 'ERROR', but connectors write 'error' (lower case). It never matches.

app/dashboard/page.tsx:36 · app/api/dashboard/route.ts:36

MediumB20. Insight priority colours never show.

The UI expects HIGH/MEDIUM. The generator emits High/Medium/Critical.

InsightsPanel.tsx:106 · lib/insights-generator.ts:30

HighB21. Loading the Memory page deletes real memories.

Every GET deletes rows titled "Decision Captured" or "Discussion Summary" (leftover mock cleanup). But the Add form placeholder suggests the title "Decision Captured", so users' own entries get deleted.

app/api/memory/route.ts:23-32 · AddMemoryModal.tsx:72

MediumB22. Deleted synced documents come back on the Memory page.

GET merges in Documents, but DELETE only removes orgMemory. So a deleted document row reappears on reload.

memory/page.tsx:450-457

HighB23. Login errors are hidden and a fallback password exists.

Login errors are shown with alert(), so the error banner can never show. There is a fallback password "password123". "Remember me" is never sent; the cookie is fixed at 24 hours.

app/lib/auth-context.tsx:78, 91-94

MediumB24. Marking a broadcast notification as read clears it for everyone.

Broadcast rows have userId null. Marking one as read changes the shared row, so it is read for all users.

notifications route 35-45 · [id]/read 18-21

MediumB25. The Autonomous Actions panel is always empty.

It reads DashboardAction, but nothing ever writes to that table.

page.tsx:44

MediumB26. Manual upload has no limits or checks.

No file type check on the server. .doc files are sent to mammoth, which only reads .docx. No size limit. No contentHash dedupe, so the same file is stored twice. Each chunk is embedded one by one while the request waits.

app/api/sources/upload/route.ts

HighB27. The embedding fallback silently ruins search.

If text-embedding-3-small fails, the code falls back to ada-002. Both make 1536-number vectors, but they live in different "vector spaces", so comparing them gives nonsense. This happens silently. Embeddings are also not batched.

lib/openai.ts:16-51

MediumB28. The match_chunks() database function is unused.

It is defined but nothing calls it. It also has no source filter, so it would ignore permissions if used.

scripts/init-pgvector.ts:60-91

MediumB29. The chunker is simpler than its comment says.

It splits on whitespace only, despite the comment. tokenCount is really a word count. A 400-word document gets a duplicate 50-word chunk.

modules/ai/chunker.ts

MediumB30. Notion database sync is probably broken on the new client. unverified

On @notionhq/client v5, databases.query moved to data_sources. The database step is probably broken. This was not verified.

modules/sources/connectors/notion.ts

Found while writing the companion docs

MediumB31. /api/ask returns 500 when you are logged out.

The catch block sends every error back as HTTP 500, including "Unauthorized". Other routes return 401. It also sends the raw error message to the browser.

app/api/ask/route.ts:351-358

MediumB32. Chat history drops earlier messages that repeat the question.

The history filter removes any earlier message whose text equals the new question. So if a user asks the same thing twice, the earlier turn vanishes from the context.

app/api/ask/route.ts:118

MediumB33. Gmail and manual uploads get the wrong freshness rate.

The ask route reads the source type from meta.file_type ?? meta.source_type. Connectors that write another string, such as gmail or manual_upload, fall back to the default decay of 0.5 points per day.

app/api/ask/route.ts:221

MediumB34. GitHub never checks if a chunk insert failed.

The result of the Supabase insert is ignored. A failed insert leaves a document with missing chunks and no error.

modules/sources/connectors/github.ts:300-315

MediumB35. Linear retries rate limits forever.

On HTTP 429 (too many requests) the Linear fetch calls itself again with no upper limit. A long rate limit can keep a sync running without end.

modules/sources/connectors/linear.ts:34-40

MediumB36. Slack and Linear use a different hash.

They hash content with MD5. The other connectors use SHA-256. It still works for spotting changes, but it is inconsistent.

modules/sources/connectors/slack.ts:189 · modules/sources/connectors/linear.ts:196

MediumB37. POST /api/documents computes a hash but never uses it.

It creates a contentHash but never compares it, so duplicates are not caught. It also never updates itemsIndexed.

app/api/documents/route.ts

MediumB38. Insight IDs can mix between requests.

Insight IDs come from one counter at module level (dyn-insight-N). Two requests running at once share it, so IDs are not stable.

lib/insights-generator.ts:23, 40, 63

MediumB39. The pgvector setup script says "completed" even when a step fails.

Each failed step is only logged. A database can look ready when the vector column or index is missing.

scripts/init-pgvector.ts

MediumB40. Package list problems.

Installed but not imported anywhere: ai, docx, gsap, the 4 @radix-ui/* packages, class-variance-authority, cross-env. dotenv is used in workers/index.ts but not declared in package.json.

package.json · workers/index.ts

MediumB41. A second PostCSS config names a plugin that is not installed.

postcss.config.mjs uses @tailwindcss/postcss, which is not in package.json. It sits next to the working postcss.config.js. Delete one of them.

postcss.config.mjs · postcss.config.js

D. Missing (never built)

These features are implied by the UI, the marketing or the plans, but there is no code for them.

MediumD1. Automatic sync.

No cron or repeatable jobs. BullMQ (the job queue library) is unused. The Drive and Notion webhooks are stubs. There are no Slack, GitHub, Linear or Gmail webhooks, and no watch channel registration (asking Google to notify us of changes).

MediumD2. Removing items deleted upstream.

5 of 6 connectors never purge items that were deleted in the source app. Only Notion does.

MediumD3. Incremental sync.

No connector fetches only what changed. Every sync starts over.

MediumD4. Token revocation on disconnect.

Disconnecting a source does not revoke the OAuth token with the provider.

MediumD5. Content that connectors skip.

  • Slack: thread replies, private channels, anything past 200 channels, a 500 messages per channel cap, and one doc per channel.
  • Drive: shared drives, Slides, xlsx, sheets after the first, subfolder paging.
  • GitHub: code, docs, wikis, issue/PR comments. It fetches only the README, 100 issues and 50 PRs.
  • Gmail: attachments.
  • Notion: database properties, many block types.
  • Linear: comments past the first page, projects, docs, anything past 1000 issues.

MediumD6. Better retrieval.

No follow-up rewriting, no hybrid keyword + vector search, no reranking, no dedupe, no OrgMemory as context, and no citations with chunk ids.

MediumD7. Team management.

No invite token + accept flow, no change role, no remove member from workspace, no edit/delete roles, no edit teams. No per-user chats: ChatSession has no userId.

MediumD8. Account features.

No email verification, profile update, session revocation, Google sign-in, real 2FA or SSO.

MediumD9. API keys that work.

Keys are never checked. They are stored as bcrypt hashes with no lookup prefix, so they cannot be found quickly. lastUsedAt is never written. There is no public API.

MediumD10. Audit log.

Only password change writes an entry (settings/password/route.ts:51). ipAddress is never set.

MediumD11. Notifications.

Only a member invite creates one.

MediumD12. Billing and plans.

No Stripe. The plan "trial" never changes. Limits are not enforced.

MediumD13. Workflow engine.

No triggers, conditions or actions.

MediumD14. Memory features.

No automatic extraction of memories. No real snapshots with restore.

MediumD15. More connectors.

HubSpot, Microsoft 365, Jira and Confluence do not exist.

MediumD16. Production basics.

  • No tests or CI.
  • No env validation: all clients fall back to dummy values, except ENCRYPTION_KEY.
  • No Prisma migrations (only db push).
  • No logger or Sentry (error tracking).
  • No root error.tsx / global-error.tsx / not-found.tsx.
  • No rate limits beyond /api/ask.
  • No security headers (next.config.ts is empty).
  • No stronger crypto.

Implementation plan

Estimates assume one developer. Size chips: S under 1 day, M 1–3 days, L 1 week or more.

Phase 0 — Lock it down

About 2–3 days. Closes the security holes in section A.
  1. Rotate the Gmail password. Remove all hardcoded fallback secrets. Fail fast (refuse to start) if JWT_SECRET or email credentials are missing. S
  2. Add auth() + a workspace check to the 7 open routes. Check session ownership in /api/ask. S
  3. Add a middleware.ts redirect for /dashboard. S
  4. Remove the no-password login path and _devPassword. S
  5. Use a separate key for OAuth state. Check the nonce in callbacks. S
  6. Add permission checks on roles, settings, API keys, workflows and upload. Add new permissions settings:manage, workflows:*, apikeys:manage. Narrow Viewer's sources:read. M

Phase 1 — Make what exists work

About 1 week. Fixes the broken items in section B.
  1. Fix Slack/Linear inserts to a single supabaseAdmin insert like gmail.ts; re-sync. S
  2. Wrap the connector body in try/catch so early errors set error; recover stale syncing sources. S
  3. Make the Slack/Linear callbacks trigger a real sync. S
  4. Sources UI: add the GitHub card, handle all redirects, add GitHub scope config. M
  5. Remove the mock Drive folders; show the real error; paginate. S
  6. Ask UI: handle no_knowledge and error; return the saved message id; fix up/positive; read ?q=; share with session id; read PDF/DOCX attachments on the server. M
  7. Small fixes: the 'error' case, High/HIGH, delete the memory mock cleanup, login error banner + password123, per-user notification read state. S

Phase 2 — Real sync engine

About 1–2 weeks.
  1. Enqueue jobs to sourceQueue; run the worker as a second docker-compose service; fall back to a direct call when there is no Redis. M
  2. Save syncSchedule; use BullMQ repeatable jobs; wire the Auto re-sync toggle. M
  3. All connectors: purge, set updatedAt from the source date, share one withRetry, count itemsIndexed correctly. M
  4. Incremental sync: Gmail history.list (fix the query override), Drive changes.list, Slack oldest, Linear updatedAt filter. L
  5. Write a sync-history row per run; send a notification on sync failure. S
  6. Revoke provider tokens on disconnect. S
  7. Webhooks: Drive changes.watch + renewal, Notion signature check; both enqueue jobs. M

Phase 3 — Team and account basics

About 1–2 weeks. Can run in parallel with Phase 4.
  1. Invite token, an accept page where the user sets their own password, resend/revoke. M
  2. Change role, remove from workspace, edit/delete roles, edit teams, add existing users. M
  3. Add userId to ChatSession; private chats with optional share. S
  4. Wire up the Profile page and link to it. S
  5. Email verification; a session version on User (so old sessions can be ended). M

Wrong claims in CLAUDE.md

The project's CLAUDE.md says every connector does two things that only Notion actually does:

  1. Purge of removed documents. CLAUDE.md says all connectors "purge documents no longer present upstream". In the code, only Notion does this (notion.ts:129-147).
  2. withRetry. CLAUDE.md says provider calls go through a withRetry wrapper. In the code, withRetry exists only in notion.ts (line 375).

One smaller mismatch: CLAUDE.md lists "OAuth client id/secret/redirect pairs per provider". In the code, only GOOGLE_REDIRECT_URI and GMAIL_REDIRECT_URI exist. The other providers build their redirect URI from the request origin.

Anyone relying on CLAUDE.md should know this until it is corrected (or until Phase 2, task 3 makes it true).
