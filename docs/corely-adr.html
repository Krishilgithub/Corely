Corely Architecture Decisions

An Architecture Decision Record (ADR) is a short note that says what we chose, why we chose it, and what it costs us.

These decisions were never written down at the time. Every record below was rebuilt from the code on 2026-10-04. The dates are "reconstructed": each one is the first day the main evidence file shows up in git history (git log --follow --format=%ad --date=short -- <file> | tail -1), or the day a key line first appeared (git log -S). All 67 commits in the repository are by Krishil Agrawal, so he is listed as the decider. That is an inference from git, not a confirmed fact.

How this log was built

  • We read the code on branch master without changing it. The main files were package.json, prisma/schema.prisma, lib/*.ts, app/api/ask/route.ts, modules/sources/connectors/*.ts, modules/ai/chunker.ts, scripts/init-pgvector.ts, workers/index.ts, Dockerfile and docker-compose.yml.
  • For the "alternatives" we used the planning notes in the repo root (MVP_PLAN.md, NOTION_CONNECTOR.md, GOOGLE_DRIVE_CONNECTOR.md, FEATURE_2_STATEFUL_ASK.md). They show what was planned. The code shows what was built. Where the two differ, the record says so.
  • "Known issues today" come from the read-only gap audit of the same date (see Gap Analysis). Line numbers point at the code as it is on 2026-10-04.
  • One correction to CLAUDE.md: it says every connector purges deleted items and uses a withRetry wrapper. In the code, only modules/sources/connectors/notion.ts does either (purge at lines 128-147, withRetry at line 375).

Status meanings

  • Accepted The decision is in the code and still looks right.
  • Accepted – needs revisiting The decision is in the code, but the audit found real problems with it.
  • Proposed Not built yet. It comes from the implementation plan in the gap audit.

How to add a new ADR

  1. Take the next free number (the last one here is ADR-028).
  2. Copy the template below into a new card. Fill in every heading. Write "none" rather than leaving a heading out.
  3. Start with status Proposed. Change it to Accepted once the change is merged.
  4. Never delete an old ADR. If a new decision replaces it, set the old one to "Superseded by ADR-0xx" and link both ways.
  5. Add the new row to the summary table and a box to the decision map.

ADR-001

One Next.js App Router app for UI and API

Accepted
  • Date: 2026-05-26 (reconstructed, first commit)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Platform

Context

Corely is built by one developer. It needs a marketing site, a dashboard and a JSON API. Splitting these into separate services would slow every change. The ingestion work (fetching, chunking, embedding) is slow and long-running, which pulls the other way.

Decision

Build everything as one Next.js 15 App Router app ("next": "^15.5.18"). Pages live under app/, the product under app/dashboard/, and the API as route handlers in app/api/**/route.ts. Every handler returns the same envelope, { success, data|error, version }, from lib/api-response.ts. Routes that depend on the logged-in user or that stream set dynamic = "force-dynamic" so Next.js does not cache them.

Alternatives considered

  • Microservices or a separate backend. MVP_PLAN.md rejects this: "Start with a Modular Monolith, architect it like a Monorepo", because "premature architecture decisions … slow down iteration".
  • Monolith plus a separate BullMQ worker process from day one. This was the plan's "one exception". The worker exists (workers/index.ts), but syncs do not use it. See ADR-015.
  • Vercel for the app and Railway or Render for workers. Planned in MVP_PLAN.md. The repo now ships a Docker image instead (ADR-018), although the invite email still links to https://corely-khaki.vercel.app/login.

Consequences

Positive
  • One repo, one type system, one deploy. The @/* path alias reaches every module.
  • Server components such as app/dashboard/page.tsx can call prisma directly.
  • A uniform response envelope makes the client code simple.
Negative
  • Long jobs run in the same process as user requests (ADR-015).
  • Landing-only libraries (GSAP, Framer Motion, react-three-fiber, Lenis) share a bundle graph and an image with the product.
  • Sections are split between app/components/ and components/landing/, so edits must check both.
Known issues today
  • HighNo middleware.ts. The dashboard is only guarded by a client-side redirect in app/lib/auth-context.tsx:65-70. See ADR-021.
  • MediumNo root error.tsx, global-error.tsx or not-found.tsx. next.config.ts is empty, so there are no security headers.
  • MediumThe ai package (^6.0.191) is installed but nothing imports it.

ADR-002

Store vectors in PostgreSQL with pgvector

Accepted
  • Date: 2026-05-26 (reconstructed, scripts/init-pgvector.ts first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Data

Context

RAG (retrieval-augmented generation: find relevant text first, then let the model answer from it) needs a place to store embeddings and search them by similarity. An embedding is a list of numbers that stands for the meaning of a piece of text. The app already uses Postgres for everything else. Keeping a second database in sync costs time and money.

Decision

Keep embeddings in the same Postgres database, in document_chunks.embedding vector(1536), using the pgvector extension. Search with cosine distance (<=>) in raw SQL. Index it with HNSW (a fast approximate nearest-neighbour index), m = 16, ef_construction = 64, and fall back to ivfflat with lists = 100 on pgvector older than 0.5.0. The database is hosted on Supabase.

Alternatives considered

  • Pinecone or Qdrant. MVP_PLAN.md planned "a vector database (Pinecone / Qdrant)" and a vector-store.ts client. Not chosen in the code: a separate store means a second bill, a second sync path and no SQL join to documents for workspace and source filters.
  • LangChain.js or LlamaIndex vector store wrappers. Planned as the "RAG Framework". Not used; queries are hand-written SQL.
  • The match_chunks() SQL function through Supabase RPC. FEATURE_2_STATEFUL_ASK.md describes calling it. The function exists but the ask route does not call it (see issues).

Consequences

Positive
  • One database. Vector search can join documents and filter by workspace_id and source_id in one query.
  • Deleting a document cascades to its chunks (onDelete: Cascade).
  • No extra vendor.
Negative
  • Prisma cannot read or write the column (Unsupported("vector")), which forces ADR-003 and ADR-004.
  • The dimension 1536 is fixed in SQL. Changing the embedding model means a new column and a full re-embed.
Known issues today
  • Mediummatch_chunks() (scripts/init-pgvector.ts:60-91, threshold 0.6, count 5) is defined but never called, and it has no source filter. It drifts from the real query in app/api/ask/route.ts:162-179 (0.55, 8).
  • MediumA fresh database cannot answer anything until npx tsx scripts/init-pgvector.ts runs. Each step only logs on failure, so a half-set-up database looks fine.

ADR-003

Prisma with @prisma/adapter-pg, plus a Supabase service-role client for the vector column

Accepted – needs revisiting
  • Date: 2026-05-26 (reconstructed, lib/db.ts and lib/supabase.ts first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Data

Context

The team wanted a typed ORM for normal tables. But Prisma skips Unsupported("vector") columns on write, so it cannot store embeddings. Something else must write that one column.

Decision

Use two clients against the same Postgres tables. lib/db.ts builds Prisma on a pg Pool through @prisma/adapter-pg (a driver adapter, so Prisma talks through the plain pg library), with engineType = "library" in the schema. lib/supabase.ts exports supabaseAdmin, a Supabase client with the service-role key (full access, server only). Rule: anything that touches embedding goes through supabaseAdmin or raw SQL; everything else goes through Prisma.

Alternatives considered

  • Prisma raw SQL for chunk inserts too ($executeRaw with ::vector). This would remove the second client. The read path already does this in app/api/ask/route.ts:162. It was not used for writes, likely because the Supabase insert was quicker to write.
  • Drizzle or Kysely, which can model a vector column. Not considered in the planning docs; MVP_PLAN.md names Prisma as the ORM.
  • Supabase client for everything. Loses Prisma types and the schema file.

Consequences

Positive
  • Typed models for 20 tables in prisma/schema.prisma.
  • The pg adapter works with Supabase's pooled connection strings.
Negative
  • Two ways to write the same table. Easy to mix up, as Slack and Linear show.
  • The service-role key bypasses Supabase row-level security entirely.
  • @prisma/adapter-pg and pg sit in devDependencies although the app needs them at run time (see ADR-018).
Known issues today
  • CriticalSlack and Linear chunks never get embeddings. They call prisma.documentChunk.create() (slack.ts:243-251, linear.ts:244-252) and then supabaseAdmin.from("document_chunks").insert() with the same id (slack.ts:253, linear.ts:254). The second insert fails on the duplicate key and is only logged. Rows keep embedding = NULL, so the similarity filter never returns Slack or Linear content.
  • MediumThe public anon client (lib/supabase.ts:15-18) is exported but unused.

ADR-004

Change the schema with prisma db push and a pgvector setup script, no migrations

Accepted – needs revisiting
  • Date: 2026-05-26 (reconstructed, prisma:push script in first package.json)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Data

Context

Early on the schema changed almost daily. Migration files add a step to every change. Also, Prisma cannot create the vector column, so some SQL has to live outside Prisma anyway.

Decision

Sync the schema straight to the database with npm run prisma:push (prisma db push). There is no prisma/migrations folder. Run npx tsx scripts/init-pgvector.ts once per database to enable vector, add embedding vector(1536), build the HNSW index and define match_chunks().

Alternatives considered

  • prisma migrate with the vector SQL in a hand-edited migration. Safer and repeatable, but slower while the schema was moving. Now proposed in ADR-024.
  • Hand-written SQL schema, as sketched in GOOGLE_DRIVE_CONNECTOR.md (CREATE TABLE document_chunks … embedding vector(1536)). Dropped in favour of the Prisma schema.

Consequences

Positive
  • Fast iteration. One command applies any schema change.
Negative
  • No history of schema changes and no safe rollback.
  • db push can drop columns or data when a field is renamed.
  • Two setup steps must run in order (push, then the script). The Dockerfile and compose file both document this by hand.
Known issues today
  • HighNo migrations is listed as a production gap in the audit (Phase 7).
  • Mediuminit-pgvector.ts swallows each failure with console.error (scripts/init-pgvector.ts:16-17, 32-33, 53-54, 93-94) and still ends with "completed".

ADR-005

Custom JWT session cookie (jose, HS256, 24h)

Accepted – needs revisiting
  • Date: 2026-05-27 (reconstructed, lib/auth-server.ts first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Auth / Security

Context

Every API route must know who the user is and which workspace they belong to. A hosted auth product adds a vendor and its own user table. A small hand-built session gives full control over the user and workspace model.

Decision

Sign a JWT (a signed token that carries the user id) with jose, HS256, setExpirationTime("24h"), and store it in the corely_session cookie. auth() verifies the token, loads the User with its Workspace and WorkspaceRole, and throws "Unauthorized" on failure. Route handlers catch that exact message and return 401. auth() also "auto-heals" any role: "admin" user with no roleId by giving them the Admin role. Passwords are hashed with bcryptjs.

Alternatives considered

  • Clerk. MVP_PLAN.md listed "Clerk (or NextAuth.js)" and a folder for "Clerk webhooks". Not chosen: a paid vendor, and a second source of truth for users and workspaces.
  • NextAuth.js (Auth.js). Also planned. Would give Google sign-in and session rotation for free, but the plan's "Email/password auth + Google OAuth" was cut to email and password only.
  • Database sessions (a session row per login). Allows real logout and revocation, at the cost of a DB read per request. auth() already does a DB read per request, so the cost would be small.

Consequences

Positive
  • No vendor; about 90 lines in lib/auth-server.ts.
  • One auth() call gives user, workspace and role to every route.
Negative
  • No server-side session list. Logout only deletes the cookie; a changed password does not end other sessions.
  • The same encrypt() signer is reused for other tokens (OAuth state), which mixes purposes.
  • No Google sign-in, email verification, 2FA or SSO.
Known issues today
  • CriticalFallback secret "fallback-secret-for-development-only" at lib/auth-server.ts:6. If JWT_SECRET is unset in production, anyone can forge sessions.
  • CriticalLogin sets the password for any user with no passwordHash ("MVP Legacy Migration Logic", app/api/auth/login/route.ts:69-78). That is an account takeover path.
  • CriticalOAuth state is signed with the session key and carries userId and workspaceId (e.g. app/api/sources/notion/connect/route.ts:23-24). It is plausibly usable as a session cookie for 24h. See ADR-022.
  • HighThe login rate limiter is an in-memory, per-process Map keyed by email (login/route.ts:14-17).
  • High"Remember me" is never sent; the cookie is always 24h. Password-reset tokens are stored in plain text (forgot-password line 29).

ADR-006

RBAC as a JSON permission list on WorkspaceRole, with 4 default roles

Accepted – needs revisiting
  • Date: 2026-05-28 (reconstructed, lib/rbac.ts first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Auth / Security

Context

Workspaces need different levels of access (admins, builders, read-only users). Custom roles were wanted too. RBAC means role-based access control: each user gets a role, and each role has a list of allowed actions.

Decision

Store permissions as a JSON string array, WorkspaceRole.permissions Json @default("[]"). lib/rbac.ts defines 8 permissions (memory:read/write, insights:read/write, teams:read/manage, sources:read/write) and four default roles created per workspace by createDefaultRolesForWorkspace(): Admin (all), Developer, Product Manager and Viewer. requirePermission() and hasPermission() check membership; the client mirrors it with hasPermission() in app/lib/auth-context.tsx.

Alternatives considered

  • Permission and role-permission join tables. Stricter and queryable, but more tables and joins for 8 strings.
  • A fixed enum on User.role only. Simple, but no custom roles. The legacy User.role string still exists next to roleId, which is why auth() needs its auto-heal step.
  • A policy library (CASL, Oso). Not considered in the planning docs.

Consequences

Positive
  • Custom roles need no schema change.
  • The same list works on server and client.
Negative
  • No validation: the database accepts any string in the array.
  • Two role fields (User.role and roleId) can disagree.
  • No permissions exist yet for settings, API keys, workflows or upload.
Known issues today
  • CriticalAll four default roles include sources:read (lib/rbac.ts:26-55), and that permission grants every workspace source in retrieval. See ADR-012.
  • CriticalAny member can create a role with any permissions (app/api/teams/roles/route.ts:31-46), rename the workspace or change its slug (settings/route.ts:65-81), and create or revoke API keys (settings/api-keys).
  • CriticalSeven routes have no auth() at all, for example app/api/sources/[sourceId]/route.ts DELETE (lines 7-27) and app/api/chats/[sessionId]/route.ts (lines 11-56).
  • MediumThere is no UI or API to change a member's role, edit or delete roles, or remove a member.

ADR-007

Encrypt OAuth tokens with crypto-js AES

Accepted – needs revisiting
  • Date: 2026-05-26 (reconstructed, lib/crypto.ts first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: Auth / Security

Context

Each connected source stores an OAuth access token, and Google sources also a refresh token. A leaked database row should not hand out access to a customer's Notion, Gmail or GitHub.

Decision

Encrypt tokens before saving with CryptoJS.AES.encrypt(text, ENCRYPTION_KEY) and decrypt them in each connector. ENCRYPTION_KEY is the one secret with no fallback: getKey() throws if it is missing.

Alternatives considered

  • Node's built-in crypto with AES-256-GCM. Authenticated (it detects tampering) and needs no package. Now proposed in ADR-023.
  • A managed key service (AWS KMS, Supabase Vault). Stronger key handling, but another vendor at MVP stage.
  • No encryption. Rejected; NOTION_CONNECTOR.md marks tokens as "AES encrypted".

Consequences

Positive
  • Tokens are not stored in plain text.
  • Two small functions; easy to call from every connector.
  • Missing key fails loudly instead of quietly.
Negative
  • Passphrase mode: the key is derived with EVP_BytesToKey (MD5, 1 iteration). Cipher is AES-CBC with no MAC, so tampering is not detected.
  • crypto-js is discontinued.
Known issues today
  • HighWeak key derivation and no integrity check (lib/crypto.ts:9-16).
  • Mediumdecrypt() returns an empty string on a wrong key instead of throwing (lib/crypto.ts:14-15). A rotated key shows up later as a confusing provider 401.
  • MediumTokens are not revoked at the provider when a source is disconnected.

ADR-008

OpenAI text-embedding-3-small (1536 numbers) with an ada-002 fallback

Accepted – needs revisiting
  • Date: 2026-05-26 (reconstructed, lib/openai.ts and the ada-002 fallback both first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: AI / Retrieval

Context

Every chunk and every question must be turned into an embedding with the same model, or similarity scores mean nothing. The model must be cheap, because every synced document is embedded chunk by chunk. Some OpenAI keys did not have access to newer models.

Decision

generateEmbedding() in lib/openai.ts cuts input to 8000 characters and calls text-embedding-3-small. On a 403, a 404 or a "model not found" style message it logs a warning and retries with text-embedding-ada-002. Both return 1536 numbers, which matches vector(1536). The same function serves all connectors, manual upload and the ask route.

Alternatives considered

  • text-embedding-3-large (3072 numbers). Better quality, higher cost, and too large for the 1536 column without shortening.
  • Open-source models (for example via Cohere or local inference). Not in the plan; MVP_PLAN.md fixes "OpenAI text-embedding-3-small".
  • Fail instead of falling back. Safer, and now proposed in ADR-028.

Consequences

Positive
  • Low cost, good quality, one shared function.
  • Works even on keys without 3-small access.
Negative
  • 3-small and ada-002 produce vectors in different spaces. The sizes match, so nothing errors, but a mix of the two silently ruins similarity.
  • One API call per chunk; no batching.
Known issues today
  • HighSilent model switch at lib/openai.ts:16-52. The model used is not saved on the chunk, so mixed data cannot be found later.
  • MediumThe errMessage.includes("not found") check (line 32) is broad and can trigger the fallback for unrelated errors.
  • MediumNo batching: manual upload embeds chunk by chunk inside the request (app/api/sources/upload/route.ts:101-104).

ADR-009

Fixed-size word chunks: 400 words with 50 words of overlap

Accepted – needs revisiting
  • Date: 2026-05-26 (reconstructed, modules/ai/chunker.ts first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: AI / Retrieval

Context

Documents are too long to embed whole, and long chunks blur the meaning. Chunks that are too small lose context. Six connectors and the upload route all need the same behaviour.

Decision

chunkText(text, docTitle) splits text on whitespace into words, takes windows of CHUNK_SIZE = 400 words, steps forward by 350 (CHUNK_OVERLAP = 50), skips windows under 30 characters, and prefixes each chunk with [docTitle]. tokenCount is set to the word count.

Alternatives considered

  • Token-based chunks ("512 tokens each" in GOOGLE_DRIVE_CONNECTOR.md). More exact against model limits, but needs a tokenizer package. The code uses words as a rough stand-in ("approx 512 tokens").
  • Structure-aware chunks (by heading, paragraph or message). Better for Notion pages and Slack threads. The code comment says "Split into paragraphs first", but it does not.
  • LlamaIndex or Unstructured.io parsing. Planned in MVP_PLAN.md; not used.

Consequences

Positive
  • Simple, fast, no dependencies, same output everywhere.
  • The title prefix helps short chunks match on topic.
Negative
  • Splits mid-sentence and mid-table; ignores structure.
  • tokenCount is a word count, so any token budget built on it is wrong.
Known issues today
  • MediumSplits on whitespace only despite the comment (modules/ai/chunker.ts:23-24).
  • MediumA document of exactly 400 words produces a second, duplicate 50-word chunk because the loop steps 350 and runs again (chunker.ts:32-50).
  • MediumChanges must be copied to the upload route too, which calls chunkText itself (app/api/sources/upload/route.ts:101).

ADR-010

gpt-4o answers, hand-rolled SSE streaming and 6-message history

Accepted – needs revisiting
  • Date: 2026-05-26 (reconstructed, text/event-stream and take: 6 first seen in app/api/ask/route.ts)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: AI / Retrieval

Context

Answers take several seconds, so users need to see text as it arrives. The UI also needs the source list before the text, plus special events for "no knowledge" and errors. Follow-up questions ("and who approved it?") need the earlier turns.

  • Claude 3.5. MVP_PLAN.md listed "GPT-4o / Claude 3.5". Only OpenAI is wired up; the marketing site still claims Claude 3.5.
  • A per-workspace model choice. Settings saves defaultLlm, but the route ignores it.

Consequences

Positive
  • Real token streaming with no extra library.
  • Sources arrive before the answer, so citations render at once.
  • Chats are stored and resumable.
Negative
  • The event protocol is custom, so client and server must change together.
  • Only the latest question is embedded; history goes to the model but not to retrieval.
  • Model name is hard-coded.
Known issues today
  • CriticalThe route does not check that sessionId belongs to the caller's workspace (app/api/ask/route.ts:103-123). Anyone can write to and read history from another session.

ADR-011

Similarity above 0.55, top 8 chunks, and a "no knowledge" refusal

Accepted
  • Date: 2026-05-30 (reconstructed, > 0.55 and NO_KNOWLEDGE_RESPONSE first seen)
  • Deciders: Krishil Agrawal (inferred from git)
  • Area: AI / Retrieval

Context

The product promise is "answers from your own knowledge, with sources". If weak matches reach the model, it will still write a confident answer from general knowledge. That is a hallucination (a made-up answer). Too strict a cut-off hides useful matches.

Decision

In the raw pgvector query keep only chunks with 1 - (embedding <=> query) > 0.55, ordered by distance, LIMIT 8. If zero chunks pass, do not call the model. Stream a fixed NO_KNOWLEDGE_RESPONSE that ends "I will never fabricate answers from outside your connected knowledge base." The system prompt repeats the rule ("NO HALLUCINATION").

Alternatives considered

  • The 0.6 / top 5 defaults of match_chunks(). Stricter and smaller. Loosened in the route for better recall.

  • A reranker (a second model that re-scores the top results). Better precision; not built.

Consequences

Positive
  • A hard guard against invented answers; no model cost when nothing matches.
  • 8 chunks of about 400 words fit the prompt with room for history.
Negative
  • A fixed threshold does not suit every model or language. Switching to ada-002 (ADR-008) changes the score scale.
  • Pure vector search misses exact names, ids and codes.
  • Several of the 8 slots can go to chunks from one document.
Known issues today
  • HighThe UI does not render the no_knowledge event, so the guard currently looks like a hang (see ADR-010). The guard itself works.
  • MediumNo dedupe per document and no keyword search. See ADR-025.

ADR-022

A separate signing key for OAuth state, with a checked nonce

Proposed
  • Date: 2026-10-04 (proposed)
  • Deciders: Krishil Agrawal (to confirm)
  • Area: Auth / Security
  • Amends: ADR-005

Context

The OAuth state parameter (a value sent to the provider and returned in the callback, used to stop forged callbacks) is a JWT signed by the session encrypt() from lib/auth-server.ts. It carries userId and workspaceId and lands in browser history and provider logs. It is plausibly usable as a corely_session cookie for 24h. The nonce comes from Math.random() and is never checked in the callbacks.

Decision

Sign state with a separate key (OAUTH_STATE_SECRET), a purpose claim (typ: "oauth_state") and a 10-minute expiry. Make getSession() reject any token without the session purpose. Generate the nonce with crypto.randomBytes, store it in a short-lived httpOnly cookie, and compare it in every callback.

  • Keep one key but add a purpose claim. Fixes reuse, but a leak of one key still breaks both.

Consequences

Positive
  • A leaked state value can no longer log anyone in.
  • Forged callbacks (login CSRF) are blocked by the nonce check.
Negative
  • One more secret to manage; six connect and six callback routes to change.
Open questions
  • Whether to also end the current 24h sessions after the change.

ADR-023

Replace crypto-js with Node crypto AES-256-GCM

Proposed
  • Date: 2026-10-04 (proposed)
  • Deciders: Krishil Agrawal (to confirm)
  • Area: Auth / Security
  • Would supersede: ADR-007

Context

lib/crypto.ts uses crypto-js passphrase mode: MD5 key derivation with 1 iteration, AES-CBC, no integrity check, and an empty string on a wrong key. The library is discontinued.

Decision

Use Node's built-in crypto with AES-256-GCM (encryption that also detects tampering). Take a 32-byte key from ENCRYPTION_KEY (base64). Store v1:<iv>:<tag>:<ciphertext> with a random 12-byte IV per value. decrypt() throws on a bad tag. During rollout, read old crypto-js values when there is no v1: prefix, and run a one-off script that re-encrypts every stored token. Then remove crypto-js.

Alternatives considered

  • libsodium (secretbox). Also strong, but a native or WASM dependency for no extra gain here.
  • A managed key service (KMS, Supabase Vault). Better key rotation; more setup. Can come later on top of this format.

Consequences

Positive
  • Modern, authenticated encryption; one fewer package.
  • The version prefix allows key rotation later.
Negative
  • A migration script must touch every Source row. A mistake locks out all connected sources.
Open questions
  • Back up the sources table before re-encrypting.

ADR-025

Hybrid search (tsvector + pgvector) with follow-up question rewriting

Proposed
  • Date: 2026-10-04 (proposed)
  • Deciders: Krishil Agrawal (to confirm)
  • Area: AI / Retrieval
  • Amends: ADR-010, ADR-011

Context

Only the latest question is embedded (app/api/ask/route.ts:158), so "and who approved it?" finds nothing. Pure vector search misses exact names, ticket ids and error codes. Several of the 8 slots can come from one document.

Decision

First, when there is history, ask a small, cheap model to rewrite the follow-up into a standalone question, and embed that. Second, add a generated tsvector column (Postgres full-text search) with a GIN index on document_chunks.content. Keep the 0.55 refusal guard on the vector side.

  • Embed the whole history. Cheap, but old topics pull results off course.

Positive
  • Follow-ups work; exact-term questions work; more varied sources.
Negative
  • One extra model call on follow-ups; one more index to keep.
  • Needs a migration (ADR-024).
Open questions
  • The full-text language setting (english or simple) for mixed-language workspaces.

ADR-027

API-key auth with a lookup prefix

Proposed
  • Date: 2026-10-04 (proposed)
  • Deciders: Krishil Agrawal (to confirm)
  • Area: Auth / Security

Context

Settings can create API keys, but nothing ever checks them. Keys are stored as bcrypt hashes (app/api/settings/api-keys/route.ts:46), and ApiKey has only keyHash and hint. bcrypt cannot be searched, so finding the key for a request would mean comparing against every key. lastUsedAt is never written.

Decision

Issue keys as crly_<prefix>_<secret>. Store the prefix in a new indexed, unique column and a SHA-256 hash of the secret (the secret is long and random, so a slow hash is not needed). Look up by prefix, compare the hash in constant time, write lastUsedAt, and attach the workspace. Add a small public API (/api/v1/ask, /api/v1/search) that accepts Authorization: Bearer, with its own rate limit (ADR-017). Gate key management behind a new apikeys:manage permission.

Alternatives considered

  • Keep bcrypt and scan all keys. Slow and grows with the number of keys.
  • Signed JWT keys. Hard to revoke without a deny list.

Consequences

Positive
  • One indexed lookup per request; keys can be revoked and audited.
Negative
  • Existing keys cannot be converted and must be reissued.
  • A public API is a new surface to secure and version.
Open questions
  • Which permissions a key carries: the creator's role, or a scope chosen at creation.

ADR-028

Remove the silent embedding-model fallback and batch embeddings

Proposed
  • Date: 2026-10-04 (proposed)
  • Deciders: Krishil Agrawal (to confirm)
  • Area: AI / Retrieval
  • Amends: ADR-008

Context

generateEmbedding() switches to text-embedding-ada-002 on some errors (lib/openai.ts:16-52). The vectors have the same size but a different meaning, so mixed data silently breaks search. Each chunk is also a separate API call.

Decision

Remove the fallback. On a model or permission error, throw a clear error so the sync sets status: "error". Save the model name in each chunk's metadata. Add generateEmbeddings(texts[]) that sends up to about 100 inputs per request, and use it in every connector and in upload.

Alternatives considered

  • Keep the fallback but tag chunks with the model and only compare like with like. Complex, and doubles the index in practice.
  • Make the model a setting. Useful later; still must never change silently.

Consequences

Positive
  • Search quality stays consistent; failures are visible.
  • Far fewer API calls and faster syncs.
Negative
  • Keys without 3-small access stop working until fixed.
  • Existing ada-002 chunks, if any, need a re-embed (scripts/reindex.ts covers Google Drive only).
Open questions
  • How to detect chunks already embedded with ada-002, since the model was never recorded.
